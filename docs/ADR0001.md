## Context

Agentic coding tools routinely consume 100k+ tokens to *understand* a medium codebase before producing useful work. Measured baselines on Forgiven showed ~140k tokens for an initial discovery task. Published research across seven major coding agents shows a 13.7× spread in token consumption for identical tasks, driven primarily by retrieval architecture rather than model choice. Crucially, context degradation begins at approximately 40% window utilization — meaning excessive retrieval is not merely expensive but actively impairs agent reasoning quality.

Existing solutions partition into two unsatisfying camps. Lexical agentic search (grep + whole-file reads, the Claude Code / Cursor approach) is transparent but consumes 54–59% utilization. Semantic RAG approaches require infrastructure investment (vector stores, embedding pipelines, reindexing) that is operationally heavy and platform-dependent. A third path exists — graph-AST repo-mapping, validated by Aider at 4–6% utilization — but is currently locked inside one tool's implementation rather than available as a portable pattern.

The author has spent prior cycles building **Forgiven**, a terminal-based AI-first IDE in Rust. Forgiven produced significant intellectual capital (130+ ADRs, four major architectural specs, working LLMLingua compression pipeline, golden-corpus evaluation harness) but its iteration cost has risen to the point where validating new ideas is bottlenecked by IDE-shell maintenance rather than by the ideas themselves. The four architectural specs Forgiven produced — Intent Translator, Codified Context, Artifact Layer, Subagent Decomposition — all presuppose a retrieval primitive that does not yet exist as a portable artifact.

A fifth spec (TECR — Token-Efficient Code Retrieval) was authored to define that retrieval primitive: a graph-AST repo-map backbone, bounded tool contracts, a context budget governor with a 40% utilization invariant, and sub-agent isolation. The spec is host-neutral by design.

This ADR establishes a new project to realize that spec.

## Decision

Adopt the TECR specification as the charter for a new project. The project's mandate is to produce a **portable, conformance-tested implementation** of TECR Levels L1 through L4, deliverable as three artifacts:

1. **`tecr-core`** — a portable retrieval engine implementing the spec's repo-map backbone (§5), tool surface (§6), governor (§7), and sub-agent contract (§8). Pure library; no I/O dependencies.
2. **`tecr-mcp`** — an MCP server that exposes `tecr-core` over the Model Context Protocol. The primary deliverable for portability across hosts (Claude Code, Cline, Cursor, Copilot, future-Forgiven).
3. **`tecr-vscode`** — a thin VS Code extension that registers the MCP server and provides a `@tecr` chat participant. The first consumer of the MCP server, not the project itself.

The project is **not** an IDE. It is a retrieval layer with a governor that augments the user's existing agent (Copilot, Claude, Cline). The agent loop, model selection, and UI remain concerns of the host.

Forgiven is not abandoned. Its current state will be tagged on a `pre-tecr-pivot` branch and preserved as a personal research lab. The work transfers — Tree-sitter familiarity, MCP integration patterns, autoresearcher's golden-corpus harness, Insightxz-style instrumentation — but the vessel changes.

## Considered Alternatives

### Alternative A: Continue Forgiven; build TECR inside it

Realize TECR as a Forgiven internal subsystem first, generalize later.

- **Pro:** preserves continuity; reuses existing Rust/ratatui investment; keeps the deep-learning lab as the primary vehicle.
- **Pro:** the autoresearcher and Insightxz are already wired into Forgiven's process model.
- **Con:** the *spec* is portable-from-day-one (per its §1 goals); coupling its first implementation to Forgiven contradicts the spec's own design intent.
- **Con:** continues the iteration-cost problem the pivot is meant to solve. Validates the spec at one user (the author) instead of many.
- **Con:** delays distribution. TECR's value is multiplicative in adopters; gating on Forgiven-readiness is a single point of failure.

**Rejected.** The spec's portability claim becomes credible only when validated against multiple hosts. A Forgiven-first implementation would defer that validation indefinitely.

### Alternative B: Spec-only release; no reference implementation

Publish the spec, let others implement it, focus the author's time elsewhere.

- **Pro:** lowest time commitment; produces a citable artifact quickly.
- **Pro:** maximally portable in theory.
- **Con:** a spec without a reference implementation is folklore. Section 9 (the measurement harness) is meaningless without something to measure.
- **Con:** the spec contains design choices (PageRank damping, default 1024-token budget, governor thresholds) that need empirical validation. Without an implementation, those choices remain assertions.
- **Con:** loses the strategic value of being the reference implementation.

**Rejected.** The spec's credibility is downstream of someone running it. That someone should be the author, at least for v1.

### Alternative C: Build for Claude Code only (MCP server, no VS Code extension)

Skip the VS Code shim; ship only `tecr-core` + `tecr-mcp`.

- **Pro:** maximum portability claim; no host-specific code.
- **Pro:** smaller scope; faster to first usable artifact.
- **Con:** loses the largest distribution channel. VS Code's user base dwarfs Claude Code's by orders of magnitude.
- **Con:** loses access to the chat participant API, which provides a natural UX surface for the governor's user-facing decisions.
- **Con:** the author's internal newsletter audience (200+ developers/architects at Standard Bank CIB) primarily uses VS Code with Copilot; a VS Code extension is the path of least friction for internal validation.

**Rejected.** The MCP server *is* the primary artifact, but a VS Code shim is the cheapest way to get it in front of real users at scale. The shim does not compromise portability — it consumes the same MCP server that any other host would.

### Alternative D: Build in Rust to reuse Forgiven's stack

Use Rust for `tecr-core` to leverage existing familiarity and crates.

- **Pro:** carries forward the author's deepest current language stack.
- **Pro:** strong AST tooling exists (tree-sitter Rust bindings).
- **Con:** the MCP TypeScript SDK is the most mature; the Rust SDK is younger.
- **Con:** VS Code extensions are TypeScript-native. Rust would mean separate process + IPC, reintroducing the cross-process bug class the pivot is meant to escape.
- **Con:** Standard Bank's internal contributor pool reads TypeScript far more readily than Rust.
- **Con:** the hot path (Tree-sitter parsing, PageRank, budget fitting) is C-bound or trivially fast in TS. There is no Rust-justifying performance ceiling.

**Deferred to ADR-0002 (or a future ADR).** Language choice is a Phase-0 decision; the current ADR locks the project charter and the artifact shape, not the implementation language. The author's working assumption is TypeScript, but this is left explicit so it can be challenged with evidence from Phase 0 rather than asserted up front.

## Consequences

### Positive

- The TECR specification gains a reference implementation, making §9 conformance gates testable rather than theoretical.
- The MCP-server-first architecture means TECR can be adopted by any compliant host without per-host porting work.
- Iteration velocity is expected to increase materially compared to Forgiven, because the agent loop, UI, and model integration are no longer the author's responsibility.
- The work transfers strategic capital from Forgiven (Rust, terminal UX, single-user) to a broader stack (TypeScript, VS Code, multi-host) without discarding the architectural lessons.
- A natural distribution path exists via the AI Engineering Monthly newsletter and the AI Engineering Standards initiative at Standard Bank CIB.

### Negative

- The author loses Rust as the primary daily language for personal AI tooling work. Mitigated by Forgiven remaining as a research lab.
- A new repository, build pipeline, ADR series, and CI surface must be established. One-time cost.
- VS Code's chat participant and language model APIs are evolving; the extension is exposed to API churn. Mitigated by the MCP server being the primary artifact (host-replaceable).
- MCP itself is young; spec changes are likely. Mitigated by pinning SDK versions and treating MCP upgrades as deliberate work.
- Risk of scope creep if Standard Bank adopts TECR internally and demands enterprise features (multi-tenant config, telemetry sinks, support obligations). Decision on whether to accept that scope is deferred to a future ADR.

### Neutral

- Forgiven's ADR series (currently 130+) does not transfer; the new project starts a fresh ADR sequence at 0001. This is intentional — the projects share intellectual lineage but not implementation lineage.
- The four architectural specs authored under Forgiven (Intent Translator, Codified Context, Artifact Layer, Subagent Decomposition) remain valid and become *consumers* of TECR rather than peers to it. They are expected to be republished as TECR-aware revisions in due course.

## Implementation Plan

The implementation follows the six-phase plan described in the companion document `docs/implementation-plan.md`, summarized:

| Phase | Scope | Exit criterion |
|---|---|---|
| 0 | Workspace skeleton, end-to-end pipe | `@tecr hello` echoes in VS Code chat |
| 1 | AST + repo-map | Aider-quality repo-map for any repo in <500ms |
| 2 | Tool surface + MCP exposure | Claude Code completes a discovery task in <15k tokens |
| 3 | Governor + telemetry | Governor halts a synthetic runaway loop |
| 4 | Sub-agent contract + tiered offload | Reference implementation delegates to local Qwen, returns summary only |
| 5 | Measurement harness | TECR-L4 conformance claim is defensible with published numbers |

Estimated calendar duration: ~10 weeks at part-time pace.

## Acceptance Criteria

This ADR is considered fulfilled when:

1. The repository at `/Users/danebalia/Repos/tecr` exists with the package layout described in the implementation plan.
2. Phase 0 exit criterion is met (end-to-end pipe demonstrably works).
3. At least one subsequent ADR (ADR-0002 or later) has been authored, demonstrating that the ADR practice is live in the new project.

## Open Questions

- **Q2.** Whether to accept enterprise scope if internal demand emerges. Deferred.
- **Q3.** Implementation language. Working assumption TypeScript; to be confirmed in Phase 0.
